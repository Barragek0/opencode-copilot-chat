## PR #133 — DeepSeek 400 on thinking-off turns (HIGH priority)

### Problem

The `400 The reasoning_content in the thinking mode must be passed back to the API` error **recurs when thinking is OFF** for DeepSeek V4. The #123 fix (shipped in 0.5.2) only covered turns where the reasoning was surfaced as a `LanguageModelThinkingPart`. Thinking-off turns follow a different code path and were not covered.

### Root cause

With thinking OFF on the Go gateway (`/zen/go/`), the extension applies the gateway workaround for upstream bug #37635: the gateway wraps responses in `reasoning_content`, so the text is emitted as **visible `LanguageModelTextPart`** — never as a `LanguageModelThinkingPart`. The conversation history therefore contains **no thinking part** to echo, and the next turn omits `reasoning_content` on the assistant history message. DeepSeek's validator 400s.

### Fix (4 commits)

1. **`aa124db`** — new internal data part `application/vnd.opencode.reasoning+json` (`src/chatParts.ts`): a transcript-resident marker carrying the reasoning text.
2. **`3d7f277`** — the OpenAI extractor accumulates the reasoning it emitted as visible text and, after the stream completes, reports the marker part into the transcript.
3. **`7a98bc4`** — `convertMessage` reads the marker on assistant history messages and includes it in the echoed `reasoning_content` (alongside genuine thinking parts), closing the loop for the next turn.
4. **`2d70849`** — unit tests for the marker helpers (round-trip, MIME discrimination, malformed payloads). 183/183 passing.

**Scope:** the marker is scoped to the `treatReasoningAsContent` path (Go gateway + thinking off), so nothing changes for thinking-on turns (genuine thinking parts) or other transports.

### Verification

- `npm test` 183/183, `npm run lint` (strict, incl. tsc check) green.
- Scoped: no behavior change when thinking is on or for non-Go transports.

### Review note for next session

This is the **mirror image** of the #123 fix: #123 covered thinking-on turns, #133 covers thinking-off turns on the Go gateway. Both are needed for the DeepSeek 400 to be fully gone. Worth verifying locally with a thinking-off DeepSeek V4 Flash multi-turn session before merging.

## PR #135 — Duplicate models after per-model config (MEDIUM priority)

### Problem (#131)

Setting a per-model option (e.g. `reasoningEffort`) in the model picker creates a settings-only group in `chatLanguageModels.json`. VS Code then calls `provideLanguageModelChatInformation` once per configured group, and the settings-only group resolves to `configuration: {}` — no `apiKey`. The extension's SecretStorage fallback ran on **both** the groupless call and the group call, serving every model twice (7 → 14 in the report).

The earlier #106 fix only suppresses the groupless call when an `apiKey`-bearing group call was observed, so it does not cover this path.

### Fix

A group call whose `configuration` is present but carries no API key is now treated as a per-model configuration group and returns `[]` — the groupless call already served the models. Verified against the VS Code source (`languageModes.ts`): the groupless call passes no `configuration`, group calls always do, so this can't suppress the groupless path.

Per-model settings (e.g. `reasoningEffort`) are applied at request time via `modelConfiguration` and are unaffected.

### Verification

- `npm test` 180/180, `npm run lint` (strict + tsc) green.
- Scenarios preserved: #86 (key via command, no group), #106/#63 (groups carrying an `apiKey`), agent variants (no configuration schema → `configuration` always `undefined`).

### Review note for next session

Small, surgical fix (+19/−1, 2 files). `mergeable` was `UNKNOWN` at last fetch — needs a re-fetch to confirm. The logic is consistent with the existing #106 carve-out and the VS Code source confirmation is solid.

## PR #136 — Inline completions / autocomplete (LOW priority, DRAFT)

### Problem (#49)

The extension has no inline code suggestions (ghost-text completions, Copilot-style). Issue #49 is a long-standing request for FIM-style autocomplete powered by the OpenCode gateway.

### Engine decision (live-measured, not assumed)

OpenCode exposes no FIM endpoint (`/completions` probed 404 on `zen/go`/`zen`/`beta`), and every opencode-go model is reasoning-first. Live probe results:

| Model                                        | TTFB       | Total      | Hidden reasoning             |
| -------------------------------------------- | ---------- | ---------- | ---------------------------- |
| `deepseek-v4-flash` (no `reasoning_effort`)  | 1813ms     | 2264ms     | 128 chars — non-viable       |
| **`qwen3.5-plus` (`enable_thinking=false`)** | **1518ms** | **1608ms** | **0 — genuine non-thinking** |

So the default engine is **`qwen3.5-plus` with `enable_thinking: false`** — zero hidden reasoning, ~1.5s time-to-first-token.

### Implementation (`src/autocomplete/`, 12 unit tests, 192 total)

| File          | Role                                                                                                               |
| ------------- | ------------------------------------------------------------------------------------------------------------------ |
| `context.ts`  | bounded prefix/suffix window (10 lines before cursor, short suffix)                                                |
| `prompt.ts`   | fill-in-the-middle emulation with FIM tokens over `/chat/completions` (Qwen family sends `enable_thinking: false`) |
| `throttle.ts` | 300ms debounce, latest-wins, superseded runs aborted                                                               |
| `engine.ts`   | streamed chat-completions engine, 3s timeout, cancellation, pure SSE parsing                                       |
| `provider.ts` | `InlineCompletionItemProvider` (single insert at cursor)                                                           |
| `index.ts`    | registration; key resolved per request from `SecretStorage`                                                        |

**Settings:** `opencodego.inlineSuggestions` (opt-in, default `false`) + `opencodego.inlineSuggestionsModel` (default `qwen3.5-plus`).

**Probe script:** `scripts/probe-completion-latency.ts` — live latency probe (key from env only).

### Known limits

- VS Code's own BYOK inline completion path (`microsoft/vscode#318545`) is still open, so this is a standalone provider; if Copilot's ghost text is active it may compete for the same spot.

### Review note for next session

This is a **draft** and explicitly marked "needs testers." The implementation is substantial (+860/−10, 19 files) but the feature is opt-in and experimental. Recommend: do not merge until at least one local smoke test confirms ghost text appears, aborts on continued typing, and degrades cleanly on missing key / timeout. The `qwen3.5-plus` default is well-justified by the latency probe.
